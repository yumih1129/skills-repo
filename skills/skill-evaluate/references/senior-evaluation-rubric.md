# 资深 SKILL 评估量表

本量表用于 `skill-evaluate` 的客观评分、证据归因、等级判定和修正闭环。评分对象是单个目标 SKILL 的真实可用性，不是文案观感。

## 1. 评分总则

- 先门禁，后评分。硬门禁失败时，总体等级直接受限。
- 先证据，后判断。每个分数都必须能追溯到文件、章节、路径、场景走查或验证结果。
- 先场景，后印象。高分必须通过至少一个真实任务链路证明。
- 先用户影响，后修辞优化。扣分要说明会怎样影响触发、执行、交付、验收或维护。
- 核心能力不能靠外部经验补齐。若执行者必须猜测关键步骤，应扣执行确定性和流程完整性。
- 资源分级加载是优点，核心流程缺失是缺陷。不要因为 `SKILL.md` 简洁就高分，也不要因为参考资料多就高分。
- 安全与权限问题具有封顶权。即使内容完整，只要存在高风险越权或隐蔽依赖，也不能给高等级。
- 同一证据快照、同一评估模式、同一量表版本下，门禁、场景、维度分、问题分级、`raw_total` 和最终等级必须一致；若复评结果变化，必须能追溯到证据变化、规则变化、算术错误或前次误读。
- 评分和判级必须做算术校验；阈值比较、总分计算、规则触发条件出现矛盾时，以校验结果为准，原报告结论无效。
- 权威顺序：
  - 评分、门禁、等级、封顶与问题分级以本量表为准。
  - 报告结构、标题、字段和命名以 `references/report-template.md` 为准。
  - `SKILL.md` 只负责评估入口、流程顺序和交互约束。
  - 若文件之间有重复描述，以支持文件中的更具体机械规则为准，主文件中的概述不得单独扩展成新规则。

## 2. 证据等级

| 等级 | 定义 | 可支撑的结论 |
|------|------|--------------|
| `E3` | 直接证据：原文规则、可读取文件、真实路径、验证结果、可复现场景走查 | 可支撑高置信结论和 P0/P1 问题 |
| `E2` | 强间接证据：多个章节一致、流程可推导、资源职责清楚但未完全展开 | 可支撑一般评分和 P2 问题 |
| `E1` | 弱间接证据：单处模糊描述、命名暗示、依赖经验补足 | 只能支撑低置信判断，维度分不得高于 6 |
| `E0` | 无证据：未找到、不可读、未验证、仅凭期待 | 不能支撑正向高分，相关维度不得高于 5 |

证据约束：
- 维度 `9-10` 必须有 `E3` 正向证据。
- 维度 `7-8.9` 至少需要 `E2` 正向证据。
- 只有 `E1` 证据时，维度分不得高于 `6`。
- 只有 `E0` 证据时，维度分不得高于 `5`，并必须标为待确认或风险。
- P0/P1 问题使用 `E3` 证据；若因资料缺失导致 P0/P1，必须说明缺失本身如何阻塞使用。
- 重复评估同一证据快照时，维度分不得随意漂移；若任何维度分发生变化，必须给出证据变化、规则变化、算术错误或前次误判说明。

## 3. 硬门禁

硬门禁先于评分。结果为 `通过`、`失败` 或 `待确认`。

### G1 结构可加载

检查点：
- `SKILL.md` 存在且可读。
- YAML frontmatter 可解析，至少包含 `name`、`description`。
- `name` 仅使用 lowercase、数字、hyphen，且满足以下任一项：与目录名完全相同；与 `_meta.json.slug` 完全相同。
- 关键引用路径存在，或明确声明为可选资源。
- 目录结构没有明显损坏、关键文件缺失或重名冲突。

失败条件：
- 主文件缺失或不可读。
- frontmatter 缺失、无法解析或无 `description`。
- 核心流程引用的必需资源不存在且无 fallback。

封顶：
- 失败：总体 `不合格`。
- 待确认：总体最多 `合格`。

### G2 触发可信

检查点：
- `description` 同时说明“做什么”和“何时使用”。
- `description` 与正文能力范围一致，不夸大、不偏移。
- 能抽出至少 2 个正向触发请求。
- 能识别至少 1 个相似但不应触发或需限制触发的边界请求。

失败条件：
- description 过短、空泛或只写主题不写触发场景。
- description 承诺正文没有的能力。
- 真实请求下难以判断是否应触发。

封顶：
- 失败：总体 `不合格`。
- 触发范围明显过宽或过窄但仍可用：总体最多 `合格`。

### G3 主任务可达

检查点：
- 执行者读完当前 SKILL 后知道下一步做什么。
- 主流程覆盖输入、动作、输出、失败处理和闭环。
- 核心任务不依赖未说明的外部 SKILL、资料、脚本或个人经验。
- 关键决策点有规则，不只是要求执行者临场判断。

失败条件：
- 主流程不成链。
- 只有目标描述，没有可执行步骤。
- 缺少关键输入处理、输出定义或失败回退。

封顶：
- 失败：总体 `不合格`。
- 主任务可达但高频分支缺口明显：总体最多 `合格`。

### G4 边界与安全可控

检查点：
- 明确做什么、不做什么。
- 明确何时直接执行、何时询问、何时等待确认。
- 对写文件、删除、联网、运行脚本、安装依赖、处理敏感信息等风险有规则。
- 外部依赖、平台假设和权限边界有说明。

失败条件：
- 会诱导越权执行或绕过用户确认。
- 存在未披露的高风险脚本、网络或权限依赖。
- 能力边界缺失导致明显误用。

封顶：
- 严重失败：总体 `不合格`。
- 有未缓解高风险但主流程可用：总体最多 `合格`。

### G5 输出可验收

检查点：
- 定义最终交付物、格式、最低内容和完成标准。
- 能判断任务是否完成、是否需要复评。
- 修正后知道如何验证。
- 报告或产物能让下一位执行者继续接手。

失败条件：
- 只说“输出结果”，没有格式、标准或验收口径。
- 完成状态无法判断。
- 没有复评或失败处理入口。

封顶：
- 失败：总体最多 `合格`；若导致主任务不可交付，则 `不合格`。

## 4. 评分维度与权重

| 维度 | 权重 | 核心问题 |
|------|------|----------|
| D1 元数据与结构规范性 | 8% | 是否可加载、可定位、可按资源职责维护 |
| D2 触发准确性与发现性 | 10% | 是否能在正确场景触发并避免误触发 |
| D3 目标契合与边界控制 | 9% | 是否清楚解决什么、不解决什么、前提是什么 |
| D4 流程完整性 | 11% | 是否覆盖准备、执行、交付、失败、闭环 |
| D5 执行确定性 | 11% | 步骤是否具体、可复现、少猜测 |
| D6 用户交互与权限治理 | 9% | 询问、确认、授权、越权防护是否清楚 |
| D7 资源策略与渐进加载 | 8% | 核心自包含，长资料和脚本仅在当前模式需要时加载 |
| D8 安全、依赖与环境假设 | 8% | 网络、脚本、文件、敏感信息、平台假设是否可控 |
| D9 输出契约与可验收性 | 10% | 交付物、格式、验收标准是否明确 |
| D10 验证、测试与场景覆盖 | 6% | 是否要求真实走查、验证和复评 |
| D11 可维护性与可迭代性 | 6% | 是否易改、易定位问题、闭环清楚 |
| D12 领域适配与复用价值 | 4% | 是否贴合领域任务且可被复用，不是一次性提示词 |

权重总计：100%。

判级常量：
- 核心维度固定为 `D2/D4/D5/D9`。
- `优秀` 基线阈值固定为原始加权总分 `>= 9.00`。
- `良好` 基线阈值固定为原始加权总分 `>= 7.80` 且 `< 9.00`。
- `合格` 基线阈值固定为原始加权总分 `>= 6.50` 且 `< 7.80`。
- `P1` 未关闭时，总体最多 `合格`。
- 用户接受有条件交付只能改变交付建议，不能改变质量等级。
- 判级时只允许降级，不允许因后续说明、亮点或用户接受回升等级。
- 本量表版本为 `skill-evaluate-rubric/v1`，与报告模板版本 `skill-evaluate-report/v1` 一一对应；混用旧模板时，历史报告不具备可比性。

## 5. 通用评分锚点

| 分数段 | 含义 | 使用条件 |
|--------|------|----------|
| `9.0-10` | 卓越 | 直接证据充分，主场景和边界场景均稳定，只有轻微优化空间 |
| `8.0-8.9` | 成熟 | 主流程可靠，少量边缘规则可补强，不影响稳定使用 |
| `7.0-7.9` | 可用 | 主要能力可用，但存在明确短板或依赖经验的节点 |
| `6.0-6.9` | 勉强 | 可完成部分主任务，但高频场景存在断点、歧义或维护风险 |
| `4.0-5.9` | 较弱 | 需要大量额外推理或外部补充，结果不稳定 |
| `0-3.9` | 失效 | 对该维度几乎没有可用设计，或存在阻塞缺陷 |

### 固定评分工作单

每个维度必须按相同顺序计算，不得先凭印象给分再补理由：

1. 按该维度检查点在文本中的出现顺序逐项评估，并把每个检查点标为 `满足`、`部分满足`、`缺失` 或 `不适用`。
2. 只有检查点与当前 SKILL 类型无关时才能标为 `不适用`，并必须说明原因；不得为了提高分数把缺失项标为不适用。
3. 计算 `coverage_ratio = (满足数量 + 0.5 * 部分满足数量) / 适用检查点数量`。若适用检查点数量为 0，该维度不得高于 `6.0`，并标为待确认。
4. 计算 `coverage_score = floor(coverage_ratio * 100) / 10`，保留 1 位小数，不四舍五入。
5. 根据 `部分满足` 和 `缺失` 的检查点列出候选问题，并按 `P0 > P1 > P2 > P3` 标注候选优先级；同一优先级时，以文本中更靠前的检查点作为该维度的 `issue_cap` 依据。最终问题分级确认后若优先级变化，必须重算相关维度。
6. 确定 `evidence_cap`：`E3 = 10.0`，`E2 = 8.9`，`E1 = 6.0`，`E0 = 5.0`。
7. 确定 `issue_cap`：关联未缓解 `P0 = 4.9`，关联未缓解 `P1 = 7.5`，关联未缓解 `P2 = 8.5`，关联未缓解 `P3 = 9.5`；没有关联问题时为 `10.0`。
8. 确定 `mode_or_resource_cap`：仅快速把关为 `8.9`；未完整读取影响该维度的关键资源为 `7.0`；定向复评且未升级标准评审为 `8.9`；均不命中时为 `10.0`。
9. 该维度最终分 `dimension_score = min(coverage_score, evidence_cap, issue_cap, mode_or_resource_cap)`。
10. 若同一证据快照下复评得到不同检查点状态、覆盖率或维度分，必须先定位差异来源；除证据变化、规则变化、算术错误或前次误读外，后一次评分无效。

固定映射：
- `满足`：检查点在目标 SKILL 或已读取支持资源中有直接规则、直接流程、直接产物定义或可复现验证。
- `部分满足`：检查点有明确设计，但缺少关键分支、验收口径、失败处理或适用边界中的一项。
- `缺失`：未找到该检查点对应规则，或只能依赖评估者经验补齐。
- `不适用`：该检查点与目标 SKILL 的声明能力、运行平台和交付物类型无关，且不影响触发、执行、验收、安全或维护。
- 候选问题优先级选择必须稳定：同一维度内按更高优先级选择；优先级相同则按文本顺序选择更靠前者。

说明性内容：
- 各维度中的“高分表现”和“低分表现”只用于理解检查点含义，不直接参与分数计算。
- 若说明性内容与固定评分工作单冲突，以固定评分工作单为准。

扣分原则：
- 缺证据扣分，不因为“可能有”给分。
- 规则抽象但可推导，相关检查点最高只能标为 `部分满足`。
- 规则存在但分散、矛盾或难维护，相关检查点最高只能标为 `部分满足`；若矛盾影响主流程，必须标为 `缺失` 并进入问题清单。
- 关键路径依赖未声明资源，相关维度不得高于 `6.0`。
- 用户无法判断完成状态，输出契约维度不得高于 `6.0`。

## 6. 分维度细则

### D1 元数据与结构规范性

检查点：
- frontmatter 字段正确，`name`、`description` 可被平台用于发现。
- 目录名、技能名、引用路径一致。
- `SKILL.md`、`references/`、`scripts/`、`assets/` 职责分明。
- 没有无效文件、重复资料或破损引用。

高分表现：
- 结构清晰、路径可追踪、核心与支持资源分层合理。

低分表现：
- 元数据缺失、命名混乱、资源堆叠、引用不可用。

### D2 触发准确性与发现性

检查点：
- description 说明能力、触发场景、对象范围和关键输出。
- 能覆盖主要真实请求。
- 能排除相近但不适用请求。
- 正文能力支撑 description 承诺。

高分表现：
- 不读取正文也能判断何时触发；读正文后无能力落差。

低分表现：
- 描述泛化、过窄、过度营销、承诺正文没有的能力。

### D3 目标契合与边界控制

检查点：
- 目标用户、任务边界、非目标、前置条件清楚。
- 对适用/不适用情况有规则。
- 不把领域外或高风险任务默认纳入。

高分表现：
- 使用者知道何时用、何时不用、何时转交或请求确认。

低分表现：
- 边界缺失导致能力蔓延、误用或与其他 SKILL 冲突。

### D4 流程完整性

检查点：
- 覆盖启动、证据采集、分析、执行、交付、失败处理、复评。
- 关键分支和决策点清楚。
- 阶段之间有输入输出衔接。
- 没有明显跳步或断链。

高分表现：
- 执行链路完整，复杂任务也能沿流程推进。

低分表现：
- 只有原则没有流程，或流程漏掉关键阶段。

### D5 执行确定性

检查点：
- 每步动作足够具体。
- 输入、输出、通过标准明确。
- 对模糊情况有决策规则。
- 执行者不需要大量背景经验才能落地。
- 评分值与问题分级必须一致：若 D5 给到高分，不能再把“执行步骤抽象、缺少方法”升级成未缓解 P1；若确有 P1，D5 不应被打到高分。

高分表现：
- 不同执行者按同一 SKILL 能得到相近结果。

低分表现：
- 大量“分析、优化、处理”但没有方法、标准或产物。

### D6 用户交互与权限治理

检查点：
- 何时直接执行、何时询问、何时等待确认。
- 一次询问数量、问题类型、用户确认点清楚。
- 删除、覆盖、引入依赖、扩大范围等动作有授权规则。
- 用户能预期系统行为。

高分表现：
- 交互克制、必要、可控，减少无意义追问和越权。

低分表现：
- 频繁问非阻塞问题，或在关键决策上擅自行动。

### D7 资源策略与渐进加载

检查点：
- `SKILL.md` 只放核心触发、流程、决策和门禁。
- 长文档、模板、脚本、素材只在当前模式需要时放入支持目录。
- 支持资源有明确用途和加载时机。
- 删除非核心资源不影响主流程理解。
- 评分量表、报告模板等长规则应由对应参考文件承担，主文件只保留权威入口和必须执行的摘要规则。

高分表现：
- 核心自包含，资源经济，只在当前模式需要时读取，不浪费上下文。

低分表现：
- 核心规则散落在参考资料里，或 `SKILL.md` 堆满低价值背景。
- 主文件重复承载完整量表、完整模板或大量细则，导致执行入口不清、维护时容易出现多处规则不一致。

评分约束：
- 不得把“没有 `references/`、`scripts/`、`assets/` 目录”本身当作低分证据。
- 只有当资源缺失已经影响主流程理解、验证能力、自包含性、复评效率或资料承载合理性时，才可据此扣分。
- 若当前 SKILL 根本不需要额外支持目录，也可以在 D7 取得中高分。

### D8 安全、依赖与环境假设

检查点：
- 网络、脚本、安装、文件写入、删除、凭据、敏感数据处理有边界。
- 说明平台、工具、权限或环境前提。
- 外部来源和第三方内容有审查入口。
- 失败或权限不足时有 fallback。

高分表现：
- 风险可见、授权清楚、依赖可验证。

低分表现：
- 隐蔽执行高风险操作，或默认拥有未声明权限。

### D9 输出契约与可验收性

检查点：
- 输出格式、最低内容、质量标准明确。
- 能判断完成、未完成、需复评。
- 对不同模式的交付物有差异化要求。
- 结果能支持下一位执行者继续工作。
- 评估报告本身必须遵守唯一模板契约：若输出同时出现旧版 `综合判定`、多套最终结论或不同章节标题风格，D9 直接降分。

高分表现：
- 交付内容结构稳定，验收标准明确，用户能据此决策。

低分表现：
- 输出只靠自由发挥，没有验收标准。

### D10 验证、测试与场景覆盖

检查点：
- 要求代表性场景走查。
- 修改后要求复查受影响门禁和维度。
- 脚本或代码资源有运行/检查要求。
- 有回归、防误触发或失败场景验证。

高分表现：
- 不仅评估静态文本，也验证真实使用链路。

低分表现：
- 没有测试、复评或场景走查，问题容易反复出现。

### D11 可维护性与可迭代性

检查点：
- 问题能定位到章节、规则、资源或脚本。
- 修改影响范围可追踪。
- 有修正闭环、退出条件和复评入口。
- 术语一致，结构不过度耦合。

高分表现：
- 后续维护者能低成本理解、修改、验证。

低分表现：
- 规则重复矛盾，修改一处会破坏多处。

### D12 领域适配与复用价值

检查点：
- 针对目标领域有稳定方法，不只是通用建议。
- 能处理该领域常见边界和失败情况。
- 抽象程度支持复用，不是一次性对话记录。
- 与相邻 SKILL 的职责关系清楚。

高分表现：
- 对领域任务有明显增益，能被多次复用。

低分表现：
- 内容过泛、过窄或只支持单次任务。

## 7. 评估模式裁剪

### 快速把关

必评：
- G1-G5 硬门禁。
- D1、D2、D4、D5、D9。
- 至少 2 个场景：1 个正向，1 个边界或失败。

限制：
- 未完整读取支持资源时，置信度最高为中。
- 最终等级最高为 `良好`。

### 标准评审

必评：
- G1-G5 硬门禁。
- D1-D12 全维度。
- 至少 3 个场景：正向、边界、失败。

### 交付评审

必评：
- 标准评审全部内容。
- 资源引用核验。
- 输出契约和验收标准复查。
- 至少 4 个场景，包含高风险或复杂分支。

交付建议条件：
- 无 P0/P1。
- 硬门禁全通过。
- 加权总分 `>= 7.8`。
- D2、D4、D5、D9 均 `>= 7.5`。

### 引入前审查

额外检查：
- 来源、维护者、版本、发布时间或可信度线索。
- 是否包含脚本、安装、网络、凭据、文件写入、外部下载。
- 与现有 SKILL 是否触发冲突。
- 是否需要 `skill-vetter` 补充安全审查。

限制：
- 来源或安全不可确认时，不给“可直接引入”结论。

### 定向复评

必评：
- 受影响硬门禁。
- 受影响维度。
- 与修正项关联的场景。

限制：
- 定向通过不等于全局优秀。
- 若修正影响 description、核心流程、资源结构、安全边界或输出契约，升级为标准评审。

## 8. 总分计算

加权总分：
```text
raw_total = Σ(维度得分 * 维度权重)
```

维度权重按百分比折算，例如 D1 得分 8.0、权重 8%，贡献为 0.64。

四舍五入：
- 判级必须使用未四舍五入的 `raw_total`。
- 报告展示总分至少保留 2 位小数；若另给 1 位小数展示值，必须同时保留 `raw_total`，且不得用展示值判级。
- 单维度分可保留 1 位小数。
- 示例：`raw_total = 8.75` 时，基线等级只能是 `良好`；不得因接近 `9.00` 或展示口径写为 `优秀`。
- 示例：`raw_total = 8.99` 时，基线等级仍是 `良好`；只有 `raw_total >= 9.00` 才是 `优秀`。
- 示例：`raw_total = 7.79` 时，基线等级只能是 `合格`；不得因展示为 `7.8` 写为 `良好`。

## 9. 总体等级

| 等级 | 基础分数 | 说明 | 行动建议 |
|------|----------|------|----------|
| 优秀 | `raw_total >= 9.00` | 体系成熟，证据充分，真实场景稳定 | 可直接交付，可作为参考样板 |
| 良好 | `7.80 <= raw_total < 9.00` | 主能力成熟，存在非阻塞优化项 | 可使用，修正非阻塞优化项 |
| 合格 | `6.50 <= raw_total < 7.80` | 主能力基本可用，但短板明显 | 有条件使用，需修正 |
| 不合格 | `raw_total < 6.50` | 存在阻塞缺陷或结果不稳定 | 不可交付，需重构或重点修复 |

## 10. 封顶与降级规则

必须按下面的机械顺序应用，不允许自由发挥：

前置条件：
- 最终等级必须在问题优先级分级完成后才能输出。
- `R6/R7` 依赖 `P0/P1` 问题清单；如果问题清单尚未生成，只能输出基线等级和待确认规则，不能输出最终等级。
- 若报告没有问题清单却声明无 `P0/P1`，该声明无效，置信度最多为中。
- 基线判定只能输出基线判定和待确认规则；最终判定才能输出最终等级、最终等级上限和交付结论。
- 若报告把基线判定和最终判定都写成平级终局结论，报告结论无效，必须重写。

### 判级算法

```text
1. 先按 raw_total 所在区间计算 baseline_grade。
2. 初始化 final_grade = baseline_grade。
3. 完成问题优先级分级，确认是否存在未缓解 P0/P1。
4. 校验 raw_total 与 baseline_grade 的区间映射，禁止 `8.75 -> 优秀`、`8.99 -> 优秀`、`7.79 -> 良好`。
5. 逐条检查 R1-R10。
6. 每命中一条规则，就把 final_grade 下调到该规则允许的最高等级。
7. 若多条规则同时命中，取最严格结果。
8. final_grade 只能下降，不能回升。
9. 置信度、亮点、非核心维度高分、用户接受、评估者倾向，都不能把 final_grade 往上抬。
```

### 等级上限规则

| 规则 | 条件 | 等级上限 |
|------|------|----------|
| `R1` | 任一硬门禁失败 | `不合格` |
| `R2` | 任一硬门禁待确认 | `合格` |
| `R3` | 任一核心维度低于 `5` | `不合格` |
| `R4` | 任一核心维度低于 `6` | `合格` |
| `R5` | 两个及以上核心维度低于 `7` | `良好` |
| `R6` | 存在未缓解 `P0` | `不合格` |
| `R7` | 存在未缓解 `P1` | `合格` |
| `R8` | 存在高风险安全、越权、隐蔽网络或可疑脚本问题 | `合格`，若涉及未披露的写文件/删除/联网/安装/脚本执行、绕过确认、凭据或敏感信息风险、或无法审查的自动化副作用，则 `不合格` |
| `R9` | 仅快速把关、未完整读取关键资源或未做足场景走查 | `良好` |
| `R10` | 定向复评但未补做标准评审 | `良好` |

判定约束：
- `R3-R5` 只允许使用 `D2/D4/D5/D9` 这四个核心维度，其他维度不得代入。
- 最终等级不得高于按 `raw_total` 计算出的基线等级；`raw_total < 9.00` 时，最终等级绝不能为 `优秀`。
- 若已命中 `R4` 或 `R7`，最终等级不得再写成 `良好`。
- 若报告中出现“raw_total”“基线等级”“命中规则”“最终等级”互相矛盾，视为报告结论无效，必须重算。
- `R4` 的触发条件是“核心维度 < 6”，`6.5` 不得误判为命中；所有阈值比较必须按数值严格判断，不能按印象或近似等级判断。
- `R8` 的不合格条件仅指以下任一类：未披露的写文件、删除、联网、安装或脚本执行；绕过用户确认或权限边界；读取、处理或外传凭据与敏感信息；不可审查且可能产生副作用的自动化行为。
- 若关键资源缺失已影响主流程判断，除维度扣分外，总体最多 `合格`。
- 用户明确接受风险或有条件交付时，只能把交付结论写为 `有条件交付`，不得据此提升最终等级。

报告一致性规则：
- 一个报告只能保留一套总分、等级、问题清单和最终判定。
- 禁止在报告尾部残留旧版 `综合判定`、旧版 `最终结论` 或过时评分表。
- 若需要重生成报告，必须整体替换旧报告内容，不得在旧报告末尾追加新版结果。
- 简版报告也必须包含判级轨迹，且判级轨迹必须来自最终判定。
- 同一报告内不得同时存在基线判定和最终判定两套终局式摘要；基线判定只能作为基线，最终判定才能作为终判。

## 11. 置信度

| 置信度 | 条件 |
|--------|------|
| 高 | 已读取核心文件和关键资源，完成模式要求的场景走查，硬门禁与核心维度有 E2/E3 证据 |
| 中 | 已读取核心文件，但支持资源、验证或场景覆盖不完整，结论仍可指导修正 |
| 低 | 材料缺失较多、路径不可读、只做局部浏览或关键结论依赖 E0/E1 证据 |

置信度影响：
- 低置信度不能给 `优秀`。
- 关键资源缺失且影响主流程时，总体最多 `合格`。
- 报告必须列出降低置信度的具体原因。
- 置信度只能降低结论可信度，不能提升最终等级。

## 12. 问题优先级

| 优先级 | 定义 | 处理要求 | 例子 |
|--------|------|----------|------|
| `P0` | 阻塞加载、触发、主流程、交付或严重安全边界 | 必须先修，再复评 | 无 `SKILL.md`、description 失真、主流程不可执行 |
| `P1` | 高频场景会误导执行、结果不可信或用户失控 | 必须先修复，修后复查相关门禁和维度 | 缺用户确认规则、输出无验收标准 |
| `P2` | 不阻塞主流程，但影响维护、复用、边缘场景 | 纳入修复排期并复评 | 引用路径不够清楚、失败处理略粗 |
| `P3` | 表达优化、轻量增强、示例补充 | 不要求交付前关闭，除非用户指定 | 术语微调、报告可读性优化 |

## 13. 推荐报告判定短语

- `可直接交付`：硬门禁全通过，无 P0/P1，总分良好以上，且 D2、D4、D5、D9 均 `>= 7.5`。
- `有条件交付`：主能力可用，但存在 P1/P2 或明确限制，需要限定使用范围或先修关键问题；该结论不提升质量等级。
- `不可交付`：硬门禁失败、存在 P0、总分不合格或主流程无法稳定完成。
- `可引入但需安全审查`：质量合格以上，但来源、脚本、权限或依赖需 `skill-vetter` 补审。
- `建议重构`：问题集中在触发、主流程、输出契约或边界控制，局部补丁难以解决。
