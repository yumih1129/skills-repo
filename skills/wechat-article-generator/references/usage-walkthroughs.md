# 典型场景走查

本文件用于帮助执行者理解当前技能在“发布源稿整理 + 最终 HTML 导出”模式下的典型动作。它不补充核心规则，只提供与 `SKILL.md` 一致的代表性场景。

## 场景 1：用户给素材，希望先整理再输出 HTML

输入：

- 用户提供要点、草稿、Markdown 或聊天记录。
- 用户没有要求文件落地。
- 用户希望先看整理结果，再决定是否成稿。

执行：

1. 先在对话中整理出四段式发布源稿：`title / summary / cover_prompt / markdown`。
2. 检查 `title <= 64`、`summary <= 120`。
3. 检查正文 Markdown 是否忠于原文，且结构已经适合后续转 HTML，同时已经具备公众号可读性与整齐版式。
4. 主题一旦确定，读取本技能内部的主题规范，确认该主题已有的组件写法。
5. 明确必须保留的信息和需要降级表达的事实。
6. 用户确认源稿后，直接输出最终 HTML。

验收：

- 用户可见中间结果只出现在对话里；执行中间结构只允许存在于执行内存，或由同一执行上下文的内存生产者直接供应给渲染脚本的标准输入中。
- 第一中间产物是四段式发布源稿，而不是自由发挥的大纲。
- 正文 Markdown 本身已经像可发布的公众号成稿，而不是等待 HTML “补救排版”的半成品。
- 没有生成额外 Markdown、`source.json`、其他 JSON、说明文件、临时目录、隐藏 staging 文件、备份文件或其他过程文件。
- 最终交付是完整 HTML，而不是大纲或路径说明。
- 已使用组件与本技能内部对应主题规则一致。

## 场景 2：用户要求“边确认边写”，最后给出 HTML

输入：

- 用户给出主题或半成稿。
- 用户明确表示要先看结构，再看最终 HTML。

执行：

1. 在对话里给出精简源稿块：
   - 标题
   - 摘要
   - 封面提示词
   - 正文 Markdown
2. 先修正摘要的概括性、正文的章节信息量、段落节奏和重点呈现，保证它已经精炼、整齐、适合手机端阅读。
3. 对照技能内部对应的主题规则，补充该主题特有组件，例如 `eyebrow`、提示块、关键词行或表格题注。
4. 根据用户反馈先调整源稿。
5. 源稿确认后再生成对应 HTML；未要求文件落地时在对话中交付，要求文件落地时进入文件落地步骤。

验收：

- 用户可见结构确认过程留在对话中；执行中间结构不落成任何文件。
- 源稿内容与原文保持一致。
- 正文 Markdown 版式已经达标，HTML 阶段只负责主题化呈现，不负责补结构。
- `cover_prompt` 被保留在源稿中，但不进入最终 HTML。
- 过程没有外溢到文件或其他资源。
- 最终 HTML 与确认后的源稿一致。

## 场景 3：用户明确要求只落盘 HTML

输入：

- 用户先在对话中确认内容结构。
- 用户给出输出目录或 HTML 文件路径。
- 用户没有要求保留可复用源稿文件。

执行：

1. 先完成对话中的四段式发布源稿整理。
2. 将确认后的源稿与技能内部对应主题规则复对一遍，确认长度、语法、层级和版式都已达标。
3. 再把从源稿收束出的结构直接交给渲染脚本。
4. 使用 `--stdin` 写入最终 HTML 文件；标准输入必须由同一执行上下文中的内存对象直接供应，不得从 `source.json`、`article.json`、`payload.json`、临时文件、隐藏文件、`base64 < ...`、`cat ... |` 或文件重定向生成。
5. 最终回复说明实际路径、主题和验证结论。

验收：

- 用户工作区中只新增最终 HTML。
- 不生成或保留 `source.json`、其他中间 JSON、Markdown 草稿、临时目录、隐藏 staging 文件、备份文件或其他过程文件。
- 文件路径与覆盖规则符合用户要求。

## 场景 4：用户要求导出 `source.md + final.html`

输入：

- 用户希望既拿到最终 HTML，也保留可再编辑、可复用的源稿。
- 用户明确提到“导出 md + html”“保存源稿”和“完整发布资产”。

执行：

1. 先在对话中完成四段式源稿确认。
2. 将源稿写为 frontmatter + 正文 Markdown 的 `source.md`。
3. frontmatter 至少包含 `title`、`summary`、`cover_prompt`、`theme`。
4. 用同一份已确认源稿生成对应 `final.html`。
5. 回复时说明两个文件的路径、主题和验证结论。

验收：

- `source.md` 与 `final.html` 来自同一份已确认源稿。
- `source.md` 中不重复 `#` 标题。
- `cover_prompt` 只保留在 `source.md` frontmatter，不出现在 `final.html`。
- 未在任何位置生成 `source.json`、其他 `.json`、临时 Markdown、临时目录、隐藏 staging 文件、备份文件或其他过程文件。

## 场景 5：用户要求“源稿 + 微信封面图 + HTML”

输入：

- 用户通过文字明确提出“根据 xxxx 内容生成源稿、封面/封面图/微信封面/微信封面图、xxx 风格/主题/样式的 HTML”。
- 用户可能同时要求文件落地，也可能只要求当前轮交付结果包含封面图。

执行：

1. 仍先完成四段式发布源稿整理与确认。
2. 按当前技能主链路先输出最终 HTML。
3. 只有在 HTML 完成后，才进入可选微信封面图分支。
4. 封面图分支只以已确认的 `cover_prompt` 为语义基准；允许在执行上下文中优化为面向微信封面图生成的提示词，但该优化提示词不回写源稿，也不默认展示给用户。
5. 执行者自行判断当前环境是否存在可用图像生成能力，不向用户询问；若存在，则生成对应封面图；若不存在，则明确提示封面图未完成，不影响 HTML，并给出 `cover_prompt` 供用户自行生成。
6. 若用户要求文件落地，则先确定 `cover.png` 的输出计划，再由文件落地步骤在当前导出模式的默认目录或用户指定路径写出。
7. 若用户未要求文件落地，则在对话中返回当前轮实际生成出的封面图结果，不用“已生成”一句话代替交付。
8. 最终交付必须显式说明封面图分支状态；状态固定为“已生成并交付”“未生成”“已生成但未写入”三类。若状态不是“已生成并交付”，必须同时说明原因；若状态为“未生成”，还必须给出 `cover_prompt`。

验收：

- HTML 主交付先完成，封面图不反向阻塞 HTML。
- `cover_prompt` 与正文、标题、摘要保持一致。
- 优化后的生图提示词不进入最终输出物。
- 用户要求文件落地时，封面图与 HTML 资产位于同一交付目录或用户指定路径。
- 若封面图已生成但写入失败，HTML 仍视为已完成，并报告封面图写入失败路径与原因。
- 若封面图未生成，最终交付中必须包含可供用户自行生成的 `cover_prompt`。
- 用户能在最终交付中直接看到封面图状态，而不是自行猜测该分支是否执行过。

## 场景 6：用户只要最终 HTML，不要任何过程

输入：

- 用户明确表示“不要过程，只给最终 HTML”。

执行：

1. 默认判断当前技能不是最优入口。
2. 优先转交或改用 `wechat-html-composer`。
3. 若用户明确点名当前技能，则保留当前技能，但仍需先在内部整理出四段式源稿，再尽量压缩对话中展示量，然后直接输出最终 HTML。

验收：

- 不把当前技能错误地维持为默认“静默直出型”技能。
- 与 `wechat-html-composer` 的边界保持清楚。

## 场景 7：可变事实较多，先在对话里做风险收口

输入：

- 素材中包含时间、数据、版本、价格、政策或产品能力描述。

执行：

1. 在源稿整理阶段标出高风险事实。
2. 依据用户提供来源或已知约束决定保留、降级表达或移出核心论据。
3. 先确保标题、摘要和正文没有把未核验信息写成确定性结论。
4. 风险处理完成后，再按技能内部对应主题组件输出 HTML。

验收：

- 风险点在 HTML 生成前被处理。
- 最终 HTML 不依赖未核验的确定性表述。

## 场景 8：封面图失败但 HTML 主交付成功

输入：

- 用户明确要求“源稿 + 微信封面图 + HTML”。
- 四段式发布源稿已经确认，最终 HTML 已生成完成。
- 当前环境中的图像生成能力不可用、生成失败，或封面图写入 `cover.png` 失败。

执行：

1. 保持已确认源稿与已生成 HTML 不回滚、不重置。
2. 明确报告封面图未完成的具体原因，例如无可用图像生成能力、生成失败或文件写入失败；不得询问用户当前环境是否具备图像生成能力。
3. 若封面图未生成，则给出已确认源稿中的 `cover_prompt`；若封面图已生成但仅写入失败，则在能力允许时返回已生成封面图结果或其明确引用。
4. 按当前模式继续交付 HTML 主结果；若是文件落地模式，仅把封面图视为附加交付失败，不把整轮任务判定为 HTML 失败。
5. 最终交付必须显式写明“HTML 已完成 / 封面图未完成 / 未完成原因 / cover_prompt”，不得只保留 HTML 成功状态。

验收：

- HTML 主交付保持成功状态。
- 用户能清楚区分“HTML 已完成”和“封面图未完成”。
- 用户在封面图未生成时仍能拿到可自行生成的封面提示词。
- 执行者不会要求用户重新确认 HTML，也不会回滚源稿状态。
