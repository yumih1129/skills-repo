# Skill: 微信公众号 HTML 对话整理与导出器

## 核心用途

把用户输入的主题、草稿、Markdown、素材或正文先整理成标准的微信公众号 Markdown 成稿，再收束为最终 HTML。

本技能的默认外部交付顺序只有两层：

- 对话中的中间整理结果
- 最终对应的 HTML

其中，对话中的中间整理结果默认指：

- 一份可审阅的标准微信公众号 Markdown 成稿
- 必要时附带极简结构说明或待确认点

默认约束：

- 所有中间结果只放在当前对话中，不新建中间 Markdown、JSON、说明文档或过程文件。
- 用户没有明确要求文件落地时，不调用写文件流程，不额外占用用户工作区资源。
- 技能执行必须自包含：只允许依赖当前技能目录内规则、资产、脚本与用户本轮提供内容，不得把技能目录外的示例、`dataset/`、历史校准文件或外部页面当作运行前提。
- 内容确认后，最终要输出对应的微信兼容内联样式 HTML。
- 使用内置主题时，组件样式必须以本技能内部沉淀的主题规范与预设为权威标准，不允许只做“相近风格”近似。
- 第一步产出的 Markdown 必须忠于原文，不得擅自改写事实、数字、引用、顺序关系、措辞立场或用户明确要求保留的表达。
- 第一步产出的 Markdown 必须已经满足公众号内容排版与后续 HTML 转换要求，不能把结构问题留到 HTML 阶段再补救。
- 第一步产出的 Markdown 不仅要“可转 HTML”，还要已经具备微信公众号可读性：层级清晰、段落整齐、重点明确、视觉节奏稳定，不能只是机械转写。

如果用户明确要求“只要最终 HTML，不要任何中间整理过程或说明”，优先使用 `wechat-html-composer`。只有用户明确点名本技能，或明确需要“边整理边确认再输出 HTML”时，才继续使用本技能。

## 本地资源与权威顺序

1. `SKILL.md`：定义触发、边界、默认流程、门禁和交付要求。
2. `references/render-contract.md`：定义对话中间结构与最终 HTML 的映射契约。
3. `references/theme-spec.md`：定义每个主题的组件职责、结构语法和禁止漂移项。
4. `assets/theme-presets.js`：对脚本渲染有效的样式 token，必须与 `references/theme-spec.md` 保持一致。
5. `references/usage-walkthroughs.md`：提供代表性场景走查，不补充核心规则。
6. `scripts/render-wechat-article-html.js`：只在用户明确要求文件落地时使用的可选渲染脚本。
7. `scripts/verify-render-wechat-article-html.js`：只在修改脚本或落地链路后做回归验证时使用。

若规则冲突，以上方顺序靠前者为准。

## 自包含边界

本技能必须在自身目录内闭环完成，不得把技能目录外资源变成隐性依赖。

允许依赖：

- 用户当前提供的正文、素材、草稿、Markdown、截图转写结果或本地文件内容。
- 当前技能目录内的 `SKILL.md`、`references/`、`assets/`、`scripts/`、`_meta.json`。

禁止依赖：

- 技能目录外的 `dataset/`、样式样刊、示例仓库、历史评审文档或其他技能目录文件。
- 需要执行者“再去参考外部模板”才能确定主题组件长相的流程设计。
- 用技能目录外资料修补本技能内部规则缺口，然后仍宣称本技能自包含。

执行准则：

- 若技能目录内规则已经给出主题锚点，必须直接按内部规则执行，不得再向外找“更像”的样例。
- 若内部规则不足以支撑某个额外风格请求，必须明确降级到内置主题或拒绝该附加风格，不得引入外部依赖补齐。
- “自包含”指执行闭环自包含，不禁止 `_meta.json` 中存在展示性质的主页链接，但该链接不得成为执行前提。

## 核心原则

1. **对话优先**：中间输出只出现在当前对话，不转存为额外文件。
2. **Markdown 先行**：必须先整理出标准微信公众号 Markdown 成稿，再进入 HTML 阶段。
3. **HTML 收束**：内容确认后的最终交付必须是对应 HTML，而不是 Markdown、JSON 或路径说明代替品。
4. **落盘显式化**：只有用户明确要求输出路径、目录或文件落地时，才进入写文件分支。
5. **先忠实整理，后视觉排版**：先把内容讲清楚、讲准确，再决定标题、导语、章节和块位。
6. **主题固定，内容动态**：主题负责视觉语法，内容决定哪些块位出现。
7. **微信兼容优先**：只使用公众号复制链路更稳定的基础标签和内联样式。
8. **事实审慎**：涉及日期、数据、价格、政策、版本、产品能力等可变事实时，优先使用用户提供来源；无法核验时降低确定性表达。
9. **不堆过程资产**：不为了“留痕”新建过程文档、草稿文件、临时目录或等价资源。
10. **规范即标准**：主题一旦确定，`references/theme-spec.md` 和 `assets/theme-presets.js` 中已固化的组件样式就是标准答案；标题、导语、提示块、章节标题、引用、列表、表格、题注、代码块等都要对齐。
11. **禁止主题漂移**：不得把某一主题的组件借给另一主题使用，例如把 `codex-template` 的左强调线二级标题放进 `feishu-template`。
12. **未映射即回退微信原生**：若当前主题无法映射用户请求的组件或结构，必须整篇自动切换到 `wechat-native-template`，不允许继续自拟样式，也不允许局部偷回退到其他主题语法。
13. **严格配置映射**：主题输出只能从 `assets/theme-presets.js` 的 preset 与 `references/theme-spec.md` 的组件锚点直接映射，不允许执行者按“类似某主题”的主观理解临时改色、改底、改对齐、改块型。
14. **Markdown 忠实性优先**：如果“更像公众号文风”和“更忠于原文”冲突，优先保留原文事实、语义和立场，再只做最小必要排版整理。

## 能力边界

适用场景：

- 用户给要点、素材、草稿、Markdown 或正文，希望先在对话里整理，再输出公众号 HTML。
- 用户希望先得到一份标准公众号 Markdown 成稿，再确认是否转 HTML。
- 用户希望先看到标题方向、章节结构、保留信息和风险点，再确认是否输出 HTML。
- 用户明确点名本技能，要求中间过程放在对话里。
- 用户最终可能需要 HTML 文件落地，但希望先在对话里把内容整理清楚。

不适用场景：

- 用户只要最终 HTML，不要任何中间整理过程；此时优先 `wechat-html-composer`。
- 用户只要大纲、标题建议、选题建议或纯 Markdown，不要求最终 HTML。
- 用户只要求封面图、海报、插画或公众号后台发布。
- 用户要求抄袭、洗稿、规避原创检测或伪造来源。

## 输入识别

执行前提取以下信息：

- 内容来源：正文、Markdown、要点、素材、聊天记录，或本地文件路径。
- 输出模式：默认 `conversation-html`；只有用户明确要求路径或文件时才切到 `file-export`。
- Markdown 整理模式：是“忠实排版整理”还是“允许在不改变事实前提下做轻度润色”。
- 风格主题：用户指定的主题名、中文风格描述，或默认主题。
- 内容约束：标题、读者、长度、语气、必须保留的信息、必须删除的信息。
- 风险事实：是否包含需要核验的时间、数据、政策、价格、版本或产品能力。
- 主题权威规则：一旦主题确定，必须定位到 `references/theme-spec.md` 中对应主题的组件约束。

阻塞性缺口只追问一次，最多 3 个问题：

- 主题或任务目标完全不清楚，无法判断文章要写什么。
- 用户明确要求文件落地，但没有给路径，也没有允许你代定路径。
- 用户要求必须保留或必须删除的内容彼此冲突，已经影响最终 HTML 成稿。

默认规则：

- 用户未指定主题时，使用 `wechat-native-template`。
- `academic-paper-template` 是论文主题的规范名称；`wechat-default-template` 仅作为兼容别名保留。它不是默认样式，默认样式仍是 `wechat-native-template`。
- 用户未指定读者时，默认面向“对该主题有实际阅读需求的公众号读者”。
- 用户未指定字数时，按手机端舒适阅读长度自动控制。
- 用户指定的主题若命中内置主题，必须读取本技能内对应的主题规则；不能只凭名字或记忆输出。
- 用户未明确允许改写时，默认采用“忠实排版整理”，只做结构重排、断句、标题层级整理、列表化和必要的微信公众号排版整理，不主动改写原意。

## 标准微信公众号 Markdown 语法标准

Step 2 产出的 Markdown 必须是可直接审阅、可直接继续转 HTML 的标准成稿，不是松散草稿。默认采用以下固定语法子集：

- 全文只允许 1 个一级标题，且必须使用 `# 文章标题`。
- 主章节必须使用 `##`；局部小标题仅在确有必要时使用 `###`。
- 禁止出现 `####` 及更深层级，避免手机端层级失控。
- 段落之间必须留 1 个空行；不得把多段内容硬并成一个大段，也不得为了换行好看插入大量空行。
- 普通正文使用自然段，不使用伪列表、伪标题、全角装饰符或手工缩进字符模拟结构。
- 并列信息使用标准列表：无序列表只用 `-`，有序列表只用 `1.` 风格。
- 引述必须使用 `>`，不能把引用原话混入普通正文冒充作者叙述。
- 对比型信息才允许使用表格；表格必须有表头，且列含义清楚。
- 代码、命令、配置片段必须使用三反引号代码块；语言可识别时应标注语言。
- 不允许在 Markdown 正文里混入原始 HTML 标签、内联样式、占位 `div` 或仅供视觉装饰的分隔符。
- 图片信息若有真实链接，使用标准 Markdown 图片语法；若只有图片意图没有链接，只保留“图片说明/图片位置”文字，不伪造资源地址。

Markdown 结构化整理的硬约束：

- 标题必须能准确概括全文，不得偷换原文主旨。
- 导语必须先交代文章主题、对象或核心结论，不得上来堆背景材料。
- 每个 `##` 章节只承载一个主话题；不同主话题必须拆章。
- `###` 只能作为 `##` 的从属展开，不能跳级单独出现。
- 列表项必须平行、同类、可并列阅读，不能把整段散文硬拆成列表。
- 表格与代码块前后应有过渡句或说明，避免内容突然断裂。

## 公众号美化排版标准

“美化、精美、整齐”不是主观感受，而是必须满足以下排版标准：

- `层级清楚`：读者一眼能分辨标题、导语、章节、小标题、引用、表格和收尾，不出现视觉层级混乱。
- `段落整齐`：正文段落长度适中，单段通常只承载一个意思；过长段必须拆开，过碎句子不得一行一段。
- `节奏稳定`：正文、列表、引用、表格、代码块应穿插有序，避免连续堆叠多个高强调块导致页面发花。
- `重点明确`：真正重要的信息优先通过标题、导语、列表、引用或表格自然显现，而不是靠口号式加粗堆砌。
- `留白合理`：章节之间有明确呼吸感，但不能为了“好看”制造空洞页面。
- `风格统一`：最终 HTML 中每个组件都必须严格服从所选主题，不允许同文混入多个主题语法。
- `手机端友好`：成稿默认按微信公众号手机阅读体验整理，避免超长标题、超密列表、超宽表格和连续大段说明。

Markdown 阶段就必须完成的美化整理动作：

- 把冗长口语句切分为适合手机端阅读的自然段。
- 把并列观点、步骤、条件、建议整理成列表，而不是挤在逗号链里。
- 把可比较信息整理成表格，把结论性原话整理成引用。
- 给每个主要章节补上足够明确的章节标题，避免“第一部分/第二部分”这类空标题。
- 让导语、正文、收尾在信息密度上形成清晰节奏，避免全文从头到尾一个语气一个形态。

## 执行流程

### Step 1：识别任务与输出模式

先判断用户要的是：

- `对话整理后输出 HTML`
- `对话整理后再决定是否输出 HTML`
- `对话整理后落盘 HTML 文件`

若用户明确要求“不要中间过程，只给最终 HTML”，优先转交 `wechat-html-composer`；若用户已经明确点名本技能，则保留当前技能，但把中间输出压缩为最小必要对话块。

在进入内容整理前，先完成主题定位：

- 将用户主题名、别名或中文描述归一化到内置主题名。
- 打开 `references/theme-spec.md` 与 `assets/theme-presets.js`，识别该主题的标题、导语、提示块、章节标题、引用、表格、题注、代码块等组件骨架。
- 若用户未指定主题，默认使用已内置的 `wechat-native-template` 规则。

同时确定 Markdown 整理策略：

- 若输入已经是连续正文或较完整 Markdown，默认以“忠实整理”为主，不改原意。
- 若输入是要点、摘录、聊天记录或碎片素材，先只做信息归并与顺序整理，再成稿为标准 Markdown。
- 若用户明确要求润色、压缩、扩写、重写，必须先锁定哪些内容可改、哪些事实不可改。

### Step 2：先整理出标准微信公众号 Markdown 成稿

这是本技能的第一核心交付步骤，必须先完成。

Markdown 成稿必须同时满足两类要求：

- `内容忠实`：与原文事实、数字、引述、判断关系、语气边界保持一致。
- `可转 HTML`：标题层级、段落、列表、引用、表格、代码块等结构已经符合后续 HTML 转换要求。
- `公众号可读`：已经具备适合公众号阅读的整齐版式、清楚层级和稳定节奏，不依赖 HTML 阶段“补排版”。

执行规则：

1. 先抽取原文中必须保留的信息单元：
   - 标题或核心主题
   - 所有明确事实、数字、时间、引用、结论
   - 用户明确要求保留的措辞、段落或顺序
2. 再做最小必要的公众号化整理：
   - 断开过长段落
   - 统一标题层级
   - 将并列信息整理为列表
   - 将明显属于引用、表格、代码的内容放回对应 Markdown 结构
3. 未经用户允许，不做以下动作：
   - 擅自增删事实
   - 擅自改写结论立场
   - 擅自合并有区别的数字或时间
   - 擅自替换引用原话
4. Markdown 阶段必须避免以下问题：
   - 把多个层级混成连续大段
   - 用视觉描述代替结构标记
   - 为了后续 HTML 好看而提前篡改原文信息
   - 用“第一部分 / 第二部分 / 其他说明”之类空泛标题敷衍章节设计
   - 让导语、正文、列表、引用、表格失去各自职责，全部压成同一种段落形态

标准 Markdown 允许的主要结构：

- `#` / `##` / `###`
- 普通段落
- 无序/有序列表
- 引用块
- 表格
- 代码块
- 图片占位说明

Markdown 阶段必须额外自检：

- 读者是否能仅通过这份 Markdown 看清文章层级与重点。
- 去掉最终 CSS 后，信息结构是否仍然成立。
- 交给另一个执行者时，是否能不猜测原文意图而稳定转成 HTML。

Markdown 阶段的输出目标不是“草稿”，而是：

- 一份可以直接审阅其内容准确性的标准公众号 Markdown 成稿

### Step 3：在对话中展示并确认 Markdown

中间整理结果只在对话中出现，默认应先展示 Markdown 成稿；必要时再附极简结构说明。

最小确认点应覆盖：

- 文章定位：写给谁，核心要讲什么。
- Markdown 标题与章节结构是否准确。
- 原文中哪些事实、案例、观点已保留。
- 哪些地方使用了最小必要整理而未改变原意。
- 哪些高风险事实需要核验、降级表达或移出核心论据。

禁止动作：

- 不生成中间 Markdown 文件。
- 不生成中间 JSON 文件。
- 不为了整理过程额外写入工作区文档。
- 不把“内部结构对象”作为对用户的主要交付格式。
- 不跳过 Markdown 审核直接凭印象输出 HTML。

如果信息已经足够，允许把结构说明压缩到最小，但 Markdown 成稿本身仍然是默认第一中间产物。

### Step 4：把 Markdown 收束为内部文章结构

按 `references/render-contract.md` 的契约，把已确认的 Markdown 成稿收束为内部文章结构。该结构可以只存在于执行上下文中，也可以在对话中以标题、导语、章节和收尾清单的形式呈现；默认不要求展示原始 JSON。

整理时必须做到：

- 以 Markdown 成稿为唯一内容基准，而不是回到原始碎片重新自由组织。
- 把 Markdown 中的标题、段落、列表、引用、表格、代码块准确映射为内部结构。
- 只在 Markdown 已经表达出真实需要时生成引用、列表、表格、代码块或图片说明。
- 不允许未知块类型、空章节、空标题或空列表进入最终 HTML。
- 对应主题规范里已有的组件，必须沿用该组件的结构和样式语法，而不是临时发明新组件。
- 若某主题规范中存在 `eyebrow`、提示块 `callout`、表格题注、关键词行或论文式前置信息，优先按该主题规范组织，而不是一律压平为普通段落。

### Step 5：输出对应 HTML

当信息足够且不再等待确认时，最终回复必须输出对应 HTML。

输出要求：

- 默认直接输出完整 HTML，而不是“稍后可生成 HTML”的说明。
- 不额外输出 JSON、Markdown 草稿、过程解释或样式说明。
- 最终 HTML 必须忠实反映已经确认的 Markdown 内容，不得在 HTML 阶段再偷偷改写内容。
- HTML 必须符合 `references/render-contract.md` 的兼容约束。
- 若当前轮仍停在用户确认阶段，则明确说明“下一步需要输出对应 HTML”，不要错误地以大纲或结构清单结束。
- 对应主题的每个已用组件都要和本技能内部已固化的主题规则保持一致，包括颜色、字号、边线、留白、圆角、对齐和题注写法。

### Step 6：可选文件落地

只有在以下条件同时满足时才进入该分支：

- 用户明确要求生成文件，或给出了输出目录/文件路径。
- 中间整理已经在对话中完成，内容不再需要额外过程文件承载。

落地规则：

- 优先使用 `scripts/render-wechat-article-html.js` 的 `--stdin` 或 `--input-base64`，避免中间文件。
- 不在用户工作区创建中间 JSON 或 Markdown。
- 若执行环境确实需要临时文件，只允许使用系统临时目录，并在完成后立即删除。
- 目标文件已存在且用户未明确允许覆盖或自动改名时，必须先询问。

## 用户交互规则

1. 信息足够时直接整理，不先给多版方案让用户选。
2. 中间输出默认放在对话里，优先展示标准 Markdown 成稿，不外溢到额外资源。
3. 用户没有指定主题时，不追问，直接使用默认主题。
4. 用户没有要求文件落地时，不主动询问输出路径。
5. 用户明确要求“只要最终 HTML、不要过程”时，优先改用 `wechat-html-composer`；若因点名当前技能而继续执行，则把中间输出压缩到最少。
6. 用户要求展示内容时，先展示 Markdown 成稿，再在确认后输出最终 HTML。

## 质量门禁

交付前必须通过：

- `触发准确`：当前任务确实需要“对话中整理 + 最终 HTML”，而不是单纯文件导出或单纯直出 HTML。
- `中间结果留在对话`：没有把结构整理写成额外中间文件或目录。
- `无额外产物`：未明确要求落盘时，不新增用户可见文件。
- `Markdown 准确`：第一步产出的 Markdown 与原文事实、数据、引用、立场和用户保留要求一致。
- `Markdown 可转 HTML`：标题层级、段落、列表、引用、表格、代码块等结构已经满足后续转换要求。
- `Markdown 语法标准`：只使用本技能允许的微信公众号 Markdown 语法子集，不混入 HTML、伪标题或伪列表。
- `排版足够美化`：Markdown 阶段已经具备清楚层级、稳定节奏、整齐段落和重点突出，不能把“美化”留给最终样式硬救。
- `结构合格`：标题、导语、章节、收尾清楚，块位没有漂移。
- `动态匹配`：列表、引用、表格、代码块和图片说明都来自内容真实需要。
- `主题一致`：已使用组件与 `references/theme-spec.md` 中对应主题规则保持一致，不混入其他主题样式。
- `示例对齐`：`assets/theme-presets.js` 或人工直写 HTML 中的内联样式，不得偏离技能内已固化的关键样式属性。
- `HTML 兼容`：基础标签稳定、样式内联、无脚本、无正文 `div`。
- `最终结果正确`：若已确认内容，最终必须输出对应 HTML；若未确认，必须明确下一步是输出 HTML，而不是结束在大纲或说明。
- `文件可验收`：只有在显式落盘时检查路径、覆盖规则和最终产物。

## 失败处理

- 主题不清楚：追问主题或目标，不猜测文章核心。
- 用户只要最终 HTML 不要过程：优先转 `wechat-html-composer`。
- 内容太少但主题明确：先在对话中整理短版结构，再输出短版 HTML。
- Markdown 与原文不一致风险：退回 Markdown 阶段，逐项对照原文修正后再转 HTML。
- Markdown 结构不适合转换：先修正标题层级、列表、引用、表格或代码块，再继续。
- Markdown 虽然正确但不够像可发布公众号成稿：继续回到 Markdown 阶段，补齐导语、章节标题、段落节奏和重点呈现，再进入 HTML。
- 用户指定的风格未内置：命中内置别名时归一化；未命中时降级到 `wechat-native-template`。
- 主题规范与预设不一致：以 `references/theme-spec.md` 为准，修正预设或直接按规范写出最终 HTML，不继续沿用旧预设。
- 文件已存在：未获允许不得覆盖；可根据用户确认自动改名。
- 图片不适合公众号：保留说明和 URL 文本，不伪造图片。
- 可变事实无法核验：使用审慎表达，或移出核心论据。
- 写入失败：报告具体路径和失败原因，请求新路径或权限。

## 复评闭环

修改本技能或本技能资源后，按以下顺序复查：

1. 检查 `SKILL.md` 是否已把默认模式改为“对话中整理 + 最终 HTML”。
2. 检查 `SKILL.md` 是否已把“标准 Markdown 成稿”固定为第一核心步骤。
3. 检查 `SKILL.md` 是否已把“标准微信公众号 Markdown 语法子集”和“美化排版标准”写成硬约束，而不是口号。
4. 检查 `references/render-contract.md` 与 `references/usage-walkthroughs.md` 是否仍然要求中间文件，或误写成“脚本直接解析 Markdown”；若有，修正为对话优先、结构收束后再渲染。
5. 抽查 `references/theme-spec.md` 与 `assets/theme-presets.js` 是否同步；若不同步，以技能内部主题规范为准修正。
6. 检查与 `wechat-html-composer` 的边界是否清楚，避免两个技能都声称默认“只输出最终 HTML”。
7. 只有在修改脚本或显式落盘链路后，才运行 `scripts/verify-render-wechat-article-html.js`。

## 最终交付格式

按任务状态选择：

- 若内容已确认，最终回复直接输出完整 HTML。
- 若当前轮仍在确认中间结构，最终回复给出对话内结构结论，并明确下一步需要输出对应 HTML。
- 若用户明确要求文件落地且已完成写入，最终回复说明实际路径、主题和验证结论；除非用户同时要求贴出 HTML，否则不重复粘贴超长 HTML。
