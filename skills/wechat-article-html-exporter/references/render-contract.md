# 渲染契约

本契约定义“对话中的标准 Markdown 成稿”如何映射为最终 HTML。它的核心目标有四个：

- 第一中间产物是可审阅的标准 Markdown 成稿
- 中间结果只保留在当前对话或执行上下文中
- 最终结果收束为微信兼容的内联样式 HTML
- 一旦主题确定，组件样式必须对齐本技能内部已固化的对应主题规范

默认不要求把中间结构保存为用户可见的 `.md` 或 `.json` 文件。只有用户明确要求文件落地时，才允许把同一结构临时交给脚本渲染，而且应优先通过内存、标准输入或 base64 完成，不新增用户可见中间产物。

重要收窄：

- 标准 Markdown 成稿是内容审阅基准与结构来源，不是当前渲染脚本直接解析的输入语法。
- 在调用 `scripts/render-wechat-article-html.js` 前，执行者必须先把已确认的 Markdown 收束为本契约的结构化对象。
- 若结构化对象与已确认 Markdown 不一致，应视为失败，退回 Markdown 阶段修正；不能假装脚本会替你纠偏。

## Markdown 中间产物

标准 Markdown 成稿是本技能的第一核心中间产物，必须满足：

- 内容忠于原文，不擅自改变事实、数字、引用、结论和立场
- 标题层级、段落、列表、引用、表格、代码块已经适合公众号内容阅读
- 结构已经可被稳定转换为内部文章结构和最终 HTML

推荐的 Markdown 结构：

```markdown
# 文章标题

导语段落。

## 第一部分

正文段落。

- 要点一
- 要点二

> 引用内容

## 第二部分

| 模块 | 说明 |
| --- | --- |
| A | B |
```

Markdown 阶段禁止：

- 把原文事实改写成更“顺”的说法
- 用纯视觉描述代替结构标记
- 在尚未确认原文准确性的情况下提前追求 HTML 视觉效果
- 把公众号排版理解为“多加边框和色块”，却不先把 Markdown 的层级、段落和重点整理好

Markdown 成稿还必须满足以下整齐化要求：

- 标题、导语、章节、小标题的职责清楚，不能互相代替。
- 每个段落表达一个主要意思，长段应先拆分再进入 HTML。
- 列表、引用、表格、代码块只在内容真实需要时出现，不得为了“好看”硬加。
- 章节标题应具有信息量，不能使用空泛编号标题充数。

## 对话中间结构

中间结构默认以对话中的结构块表达，不要求展示机器 JSON。最小结构应覆盖：

- `markdown`：已确认的标准 Markdown 成稿
- `title`：文章标题
- `theme`：主题名；未指定时默认 `wechat-native-template`
- `lead`：导语或开头摘要
- `blocks`：位于正文前的支持块，可选
- `sections`：正文章节，至少 1 个
- `closing`：收尾段落或提示块，可选

推荐的对话表达示例：

```markdown
Markdown：
# 文章标题

导语

## 第一部分
正文

标题：文章标题
主题：wechat-native-template
导语：用一段话说明文章切入点
正文结构：
1. 第一部分
2. 第二部分
3. 第三部分
收尾：一句总结或行动建议
```

当主题规范存在额外前置组件时，可在对话结构中补充：

- `eyebrow`：标题上方的小型主题标签
- `meta`：论文式或文档式前置信息
- `keywords`：关键词或关键标签行
- `callout`：标题导语之后的提示块

## 机器结构

当需要走脚本渲染或做确定性校验时，可以在执行上下文中临时转换为以下结构：

```json
{
  "markdown": "# 文章标题\n\n导语\n\n## 第一部分\n\n正文",
  "eyebrow": "可选的小型主题标签",
  "title": "文章标题",
  "meta": ["作者姓名", "团队名称", "日期"],
  "theme": "wechat-native-template",
  "lead": {
    "title": "摘要",
    "text": "导语或摘要正文"
  },
  "keywords": {
    "label": "关键词：",
    "items": ["公众号排版", "内联样式"]
  },
  "blocks": [
    { "type": "callout", "label": "System Note", "text": "..." },
    { "type": "quote", "text": "..." },
    { "type": "list", "ordered": false, "items": ["...", "..."] },
    {
      "type": "table",
      "label": "Table 1",
      "note": "表格说明文字",
      "noteEmphasis": true,
      "columnWidths": ["22%", "34%", "44%"],
      "headers": ["A", "B", "C"],
      "rows": [["1", "2", "3"]]
    },
    { "type": "code", "language": "text", "text": "..." },
    { "type": "image", "src": "...", "alt": "...", "caption": "..." }
  ],
  "sections": [
    {
      "level": 2,
      "heading": "章节标题",
      "blocks": [
        { "type": "paragraph", "text": "..." },
        { "type": "quote", "text": "..." },
        { "type": "list", "ordered": false, "items": ["...", "..."] }
      ]
    }
  ],
  "closing": [
    { "type": "paragraph", "text": "收尾内容" }
  ]
}
```

该结构默认只存在于执行内存、标准输入或 base64 参数中。除非用户明确要求 HTML 文件落地且执行环境确有需要，不得把它保留为用户可见的中间文件。

字段职责收窄：

- `markdown`：审阅基准和追溯基准，记录已确认成稿；当前渲染脚本不会直接解析它生成块结构。
- `title`、`lead`、`blocks`、`sections`、`closing`：必须是从已确认 Markdown 推导出的结构化字段，而不是绕开 Markdown 重新自由生成的文案。
- 若未携带 `markdown` 字段，执行者仍然必须确保结构化字段来自已确认 Markdown；不能因为字段缺失就跳过忠实性约束。

## 映射规则

- `markdown` -> 执行者收束内部结构时的唯一内容基准；不是当前脚本的直接解析入口
- `eyebrow` -> `h1` 之前的主题标签段落
- `title` -> `h1`
- `meta` -> `h1` 之后的前置信息段落
- `lead.title` + `lead.text` -> 导语块
- `keywords` -> 导语之后的关键词行
- `blocks` -> 标题之后、章节之前的固定支持块区域
- `callout` -> 提示块 `section > p + p`
- `sections[].level = 2` -> `h2`
- `sections[].level = 3` -> `h3`
- `paragraph` -> `p`
- `quote` -> `blockquote`
- `list` -> `ul` / `ol`
- `table` -> `table`
- `table.label` -> 表格题签
- `table.note` -> 表格副说明或图注式说明
- `code` -> `pre > code`
- `image` -> `img` + 说明文本
- `closing` -> 收尾块，通常使用段落或轻提示块

## 渲染规则

1. 先选定主题，再套用该主题的 preset。
2. 先确认 Markdown 成稿已经通过“内容准确”和“结构可转 HTML”检查。
3. 再读取本技能内部的主题规范，确认该主题已经固化的组件形态，再决定是否使用 `eyebrow`、`meta`、`keywords`、`callout`、表格题注和代码块。
4. 主题 preset 只负责把技能内部已确认的组件样式程序化，不允许脱离主题规范自行创造“差不多”的样式。
5. 内部结构必须从已确认的 Markdown 成稿推导，不得绕过 Markdown 阶段回到原始素材重新自由生成。
6. `blocks` 位于 lead 和 keywords 之后、sections 之前，`sections` 位于主章节区域，`closing` 位于正文收尾。
7. HTML 必须是完整文档，`body` 中只保留一个主要 `article` 作为复制面。
8. 所有样式都必须写入内联 `style`。
9. 不允许 `script`、`iframe`、`form`、正文 `div`、外部 CSS、动画或固定定位。
10. 未知块类型、空标题、空章节、空列表、空表格、空代码和缺少 `src` 的图片必须在渲染前失败。
11. 对技能内部主题规范中已固化的组件，颜色、留白、边线、对齐、圆角和题注写法都应保持一致。
12. “美化”必须建立在结构正确之上；如果 Markdown 还存在空标题、长段堆叠、并列关系未列表化等问题，禁止跳到 HTML 阶段硬修视觉。
13. 对当前主题无法映射的组件或结构，必须整篇回退到 `wechat-native-template`；不允许回退到 `base` 样式伪装成“也支持”，也不允许局部混入别的主题组件。
14. 允许变化的只有内容，不允许变化主题组件的样式值来源；所有主题样式必须直接来自 preset 映射，不得自行改写成“更像某主题”的另一套实现。

## 美化与整齐的落地标准

最终 HTML 至少应体现以下结果：

- `标题像标题`：`h1` 与 `h2/h3` 在视觉上有明确层级差，不得长得像普通段落。
- `导语像导语`：导语必须明显区别于正文首段，承担文章引入作用。
- `正文像正文`：正文段落节奏一致，不出现忽长忽短、忽左忽中、同层级样式乱跳。
- `重点像重点`：列表、引用、提示块、表格只突出真正重点，不形成满屏强调。
- `收尾像收尾`：结尾应有明确收束，而不是在最后一个章节中突然终止。

## 对话展示规则

- 中间结构默认用自然语言结构块、简洁清单或章节方案展示。
- 默认先展示 Markdown 成稿，再决定是否补充结构说明。
- 不用原始 JSON 作为面向用户的默认展示格式。
- 若用户要求先确认结构，再继续生成 HTML，停在结构块即可，但必须明确下一步是输出对应 HTML。
- 若用户要求立即成稿，结构整理可以压缩成一句到一段的对话说明，然后直接输出最终 HTML。
- 若主题是 `academic-paper-template`，按“论文主题”处理，可在对话中显式确认论文式前置信息、摘要和关键词行，再输出 HTML。旧键名 `wechat-default-template` 仅作兼容别名理解。

## 验证规则

- 必须包含 `<!DOCTYPE html>`。
- HTML 内容必须与已确认 Markdown 成稿一致，不能在转换阶段再改写内容。
- 必须包含 `html`、`head`、`body`、`article`。
- `body` 中必须只有一个主要 `article`。
- 不得出现禁止标签。
- 关键节点必须带内联 `style`。
- 不得把 Markdown 原文直接包成一个大段落。
- 同主题下的不同输入，只能改变内容密度，不改变块模型。
- 若将主题规范里存在的 `eyebrow`、`callout`、表格题注或关键词行省略掉，必须是因为当前内容不需要，而不是因为渲染链路不支持。
- 若某主题组件使用特殊样式，例如 `codex` 的左强调线 `h2`、`feishu` 的胶囊 `h3`、`wechat-default` 的摘要区，输出时不得替换为其他主题的通用写法。
- 若 Markdown 原稿本身仍像素材拼贴而不像可发布文章，则应判定为前序失败，而不是把责任转嫁给 HTML 样式。
- 若输出 HTML 的关键样式值与当前主题 preset 不一致，应判定为主题映射失败；若当前主题无法覆盖该结构，应自动切回微信原生主题，而不是解释为“风格发挥”。

## 输出模式规则

- 默认输出模式是：在对话中给出中间整理，然后直接输出最终 HTML。
- 用户明确要求文件落地时，可以额外写出 `.html` 文件。
- 无论是否落地，都不得把中间结构文件作为最终交付物。

## 输出路径规则

- 输出路径是已存在目录时，写入该目录下的 `wechat-article.html`。
- 输出路径是 `.html` 或 `.htm` 文件时，写入该文件。
- 输出路径是 `.md` 文件时，只把它当作命名提示，写入同目录、同 basename 的 `.html` 文件。
- 输出路径没有扩展名且不存在时，视为目录路径，写入其下的 `wechat-article.html`。
- 输出路径已存在、没有扩展名且不是目录时，必须失败。
- 目标文件已存在时，默认失败；只有显式允许覆盖或显式允许自动改名时才继续。
- 用户工作区中不得生成或保留内部结构 `.json` 文件。
