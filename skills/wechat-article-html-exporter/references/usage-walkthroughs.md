# 典型场景走查

本文件用于帮助执行者理解当前技能在“对话中整理 + 最终输出 HTML”模式下的典型动作。它不补充核心规则，只提供与 `SKILL.md` 一致的代表性场景。

## 场景 1：用户给素材，希望先整理再输出 HTML

输入：

- 用户提供要点、草稿、Markdown 或聊天记录。
- 用户没有要求文件落地。
- 用户希望先看整理结果，再决定是否成稿。

执行：

1. 先在对话中整理出标准微信公众号 Markdown 成稿。
2. 按技能内固定语法子集检查 Markdown：单一 `#` 标题、`##/###` 层级、标准列表、标准引用、标准表格与代码块。
3. 检查 Markdown 是否忠于原文，且结构已经适合后续转 HTML，同时已经具备公众号可读性与整齐版式。
4. 主题一旦确定，读取本技能内部的主题规范，确认该主题已有的组件写法。
5. 明确必须保留的信息和需要降级表达的事实。
6. 用户确认 Markdown 后，直接输出最终 HTML。

验收：

- 中间结果只出现在对话里。
- 第一中间产物是 Markdown 成稿，而不是自由发挥的大纲。
- Markdown 本身已经像可发布的公众号成稿，而不是等待 HTML “补救排版”的半成品。
- 没有生成额外 Markdown、JSON 或说明文件。
- 最终交付是完整 HTML，而不是大纲或路径说明。
- 已使用组件与本技能内部对应主题规则一致。

## 场景 2：用户要求“边确认边写”，最后给出 HTML

输入：

- 用户给出主题或半成稿。
- 用户明确表示要先看结构，再看最终 HTML。

执行：

1. 在对话里给出精简结构块：
   - 标准 Markdown 成稿
   - 文章定位
   - 风险点
2. 先修正 Markdown 的章节信息量、段落节奏和重点呈现，保证它已经精炼、整齐、适合手机端阅读。
3. 对照技能内部对应的主题规则，补充该主题特有组件，例如 `eyebrow`、提示块、关键词行或表格题注。
4. 根据用户反馈先调整 Markdown。
5. Markdown 确认后再输出对应 HTML。

验收：

- 结构确认过程留在对话中。
- Markdown 内容与原文保持一致。
- Markdown 版式已经达标，HTML 阶段只负责主题化呈现，不负责补结构。
- 过程没有外溢到文件或其他资源。
- 最终 HTML 与确认后的结构一致。

## 场景 3：用户明确要求文件落地

输入：

- 用户先在对话中确认内容结构。
- 用户给出输出目录或 HTML 文件路径。

执行：

1. 先完成对话中的 Markdown 成稿整理。
2. 将确认后的 Markdown 与技能内部对应主题规则复对一遍，确认语法、层级和版式都已达标。
3. 再把从 Markdown 收束出的结构直接交给渲染脚本。
4. 优先使用 `--stdin` 或 `--input-base64` 写入最终 HTML 文件。
5. 最终回复说明实际路径、主题和验证结论。

验收：

- 用户工作区中只新增最终 HTML。
- 不保留中间 JSON 或 Markdown。
- 文件路径与覆盖规则符合用户要求。

## 场景 4：用户只要最终 HTML，不要任何过程

输入：

- 用户明确表示“不要过程，只给最终 HTML”。

执行：

1. 默认判断当前技能不是最优入口。
2. 优先转交或改用 `wechat-html-composer`。
3. 若用户明确点名当前技能，则保留当前技能，但仍需先在内部整理出标准 Markdown，再尽量压缩对话中展示量，然后直接输出最终 HTML。

验收：

- 不把当前技能错误地维持为默认“静默直出型”技能。
- 与 `wechat-html-composer` 的边界保持清楚。

## 场景 5：可变事实较多，先在对话里做风险收口

输入：

- 素材中包含时间、数据、版本、价格、政策或产品能力描述。

执行：

1. 在 Markdown 整理阶段标出高风险事实。
2. 依据用户提供来源或已知约束决定保留、降级表达或移出核心论据。
3. 风险处理完成后，再按技能内部对应主题组件输出 HTML。

验收：

- 风险点在 HTML 生成前被处理。
- 最终 HTML 不依赖未核验的确定性表述。
